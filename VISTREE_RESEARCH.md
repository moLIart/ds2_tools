# DS2: чанк vistree

## Краткий результат

`vistree` в `DS2GeometryFile_1` версии `0.8` — разреженное адаптивное октодерево. Листья содержат индексы мешей, чьи AABB пересекают ячейку. Это **не PVS, не граф порталов и не готовый список геометрии, видимой из комнаты**.

Исследование основано на разборе всех 17 установленных `.ds2` и дизассемблировании `ds2render.dll`. Разметка записей и смысл их полей установлены. Прямое использование дерева для отбора мешей по frustum в оригинальном рендерере **не подтверждено**.

Документ самодостаточен: временные дампы дизассемблирования и история беседы для продолжения не требуются. Общий формат карты описан в [DS2_RESEARCH.md](DS2_RESEARCH.md). Состояние кода перед документированием — коммит `a39ba60`.

## Формат на диске

Обрамление такое же, как у остальных секций карты:

```text
String "DS2Chunk_begin"
String "vistree"
u32 node_count
Node nodes[node_count]
String "DS2Chunk_end"
```

`String = u16 byte_length + byte[byte_length]`, без NUL. Все числа little-endian, `f32` — IEEE 754. Padding между полями нет. Отдельной длины payload у секции нет: искать завершающий маркер внутри бинарных данных вместо разбора записей нельзя.

Смещения относительно начала одной записи `Node`:

| Смещение | Тип | Значение |
|---:|---|---|
| `+0` | `f32[3]` | `bounds_min` |
| `+12` | `f32[3]` | `bounds_max` |
| `+24` | `f32` | `sphere_radius` |
| `+28` | `f32[3]` | `sphere_center` |
| `+40` | `u8` | `is_leaf`: ноль — внутренний узел, ненулевое — лист |
| `+41` | условный хвост | Описан ниже |

Хвост зависит от `is_leaf`:

| Вид узла | Хвост | Полный размер записи |
|---|---|---:|
| Внутренний | `u32 children[8]` | 73 байта |
| Лист | `u32 mesh_count`, затем `u32 mesh_indices[mesh_count]` | `45 + 4*mesh_count` байт |

В корпусе флаг принимает только 0 и 1. Движок трактует любое ненулевое значение как лист.

### Исправление прежней интерпретации поля +24

В `inspect_ds2.py::_node()` поле пока читается как `u32` и называется `field_24`. **Это старое исследовательское имя и неверная семантическая типизация: фактически там float-радиус.** Границы записей парсер при этом определяет правильно.

Доказательства:

1. На всех 11951 узлах значение, интерпретированное как f32, совпадает с половиной диагонали AABB с погрешностью f32.
2. `0x1005CCC4–0x1005CCFD` вычисляет половины размеров AABB; `0x1005CD01–0x1005CD19` — сумму квадратов и квадратный корень; `0x1005CD43` сохраняет результат в поле узла `+0x24` в памяти.
3. Reader в `0x1005BEC4` сохраняет четыре байта радиуса именно в это поле.

Формулы:

```text
sphere_center = (bounds_min + bounds_max) / 2
sphere_radius = length(bounds_max - bounds_min) / 2
```

## Геометрия и нумерация дерева

- Корень имеет индекс 0. Это подтверждено и файлами, и обходом: стартовый указатель берётся из первого элемента массива дерева.
- `children` содержит нулевые индексы в том же массиве `nodes`, не смещения в файле и не указатели.
- `0xFFFFFFFF` означает отсутствующего ребёнка.
- Каждый существующий ребёнок занимает одну из восьми половинных ячеек родителя.
- Номер октанта задаётся битами: `slot = x_high | (y_high << 1) | (z_high << 2)`. Биты X/Y/Z имеют веса 1/2/4. Нулевой бит означает нижнюю половину по соответствующей оси.
- Листья бывают на разной глубине. Пропущенный ребёнок не заменяется отдельной пустой записью.
- Во всех исследованных файлах дерево связное, без циклов и общих детей; все узлы достижимы от 0. Сериализация соответствует обходу depth-first в порядке слотов 0…7; индексы детей больше индекса родителя.

Наблюдение по корпусу, не универсальная гарантия экспортёра: корень — куб вокруг общего AABB всех мешей. Его центр равен центру этого AABB, а сторона равна максимальному размеру AABB плюс 20 единиц, то есть по 10 единиц с каждой стороны наиболее длинной оси.

В вычислениях из f32 наблюдались абсолютные расхождения центров/границ октантов до `0.001953125` единицы и относительное расхождение радиуса до `2.06e-6`. При дальнейшей проверке структуры нельзя требовать побитового равенства вычисленных float-границ. Эти числа — измеренные погрешности корпуса, не ограничения формата.

## Семантика списков мешей

`mesh_indices` — нулевые индексы записей секции `meshes`. Это **не** индексы треугольников, VB/IB, записей `models`, источников света или runtime-областей окклюзии.

Для каждого листа всех 17 карт установлено точное равенство:

```text
stored_mesh_ids == {
    i for i, mesh in enumerate(meshes)
    if mesh.bounds_max.x >= leaf.bounds_min.x
       and mesh.bounds_min.x <= leaf.bounds_max.x
       and mesh.bounds_max.y >= leaf.bounds_min.y
       and mesh.bounds_min.y <= leaf.bounds_max.y
       and mesh.bounds_max.z >= leaf.bounds_min.z
       and mesh.bounds_min.z <= leaf.bounds_max.z
}
```

Использовались AABB, сериализованные в описаниях мешей, а не локальные координаты общих VB. Речь о закрытом пересечении: касание границ считается пересечением.

Все меши представлены хотя бы в одном листе. Внутри листа индексы строго возрастают и не повторяются. Один меш может принадлежать многим листьям; максимум в корпусе — 805 листьев на меш. При сборе мешей из нескольких ячеек нужна дедупликация.

Это пространственная broadphase-привязка: даже если AABB меша пересекает ячейку, его треугольники не обязаны фактически проходить через неё. Данных о видимости за стенами в этих списках нет.

## Представление узла в памяти движка

Размер runtime-узла — `0x90` байт. Его нельзя читать с диска через memcpy: порядок центра/радиуса отличается, а после children есть runtime-поля.

| Смещение в памяти | Содержание |
|---:|---|
| `+0x00` | AABB min, Float3 |
| `+0x0C` | AABB max, Float3 |
| `+0x18` | Центр сферы, Float3 |
| `+0x24` | Радиус сферы, f32 |
| `+0x28` | Восемь u32 индексов детей |
| `+0x48` | Runtime ID автоматической области окклюзии; изначально `FFFFFFFF` |
| `+0x4C` | Контейнер областей окклюзии, строго покрывающих узел |
| `+0x5C` | Контейнер пересекающих областей окклюзии у листа |
| `+0x6C` | Контейнер связанных объектов/мешей |
| `+0x7C` | Контейнер статических источников света |
| `+0x8C` | Флаг листа |

В этих контейнерах begin/end/capacity находятся по смещениям `+4/+8/+12` относительно начала контейнера. Не нужно считать его первым словом указатель begin. Контейнеры в файле не сериализуются.

## Поведение оригинального загрузчика

### Сохранённые mesh IDs не превращаются прямо в указатели

В `0x1005BF0A–0x1005BF33` reader читает счётчик и каждый u32 списка листа, но значения индексов **отбрасывает**. Восемь полей детей листа в памяти заполняются `FFFFFFFF`. Внутренние узлы, наоборот, сохраняют восемь прочитанных child IDs.

После чтения массива `0x1005D310` запрашивает уже существующие области у менеджера и добавляет их в дерево callback-обходом. Нельзя описывать этот путь как восстановление runtime-указателей из сохранённого массива mesh IDs.

### Непустые листья могут создавать области окклюзии

Ветка `0x1005BF7E–0x1005C028` выполняется только если:

- включён `r_occ_use_auto_placement`;
- текущий узел — лист;
- прочитанный `mesh_count > 0`.

Она создаёт область через `0x10006CE0()->0x10006350` и сохраняет её runtime ID в `node+0x48`. Следовательно, **значения IDs отбрасываются, но сам счётчик всё же влияет на поведение загрузчика**.

Точная деталь кода: перед созданием области из каждой из шести координат min/max вычитается `20.0` — константа по `0x1017F968`. Это сдвиг обеих границ, не расширение AABB. Намерение такого смещения не установлено; не заменять его в описании на «добавляет padding».

Менеджер идентифицирован строкой `COcclusionAreasManager::m_ev_on_areas_modified` по VA `0x1017F9BC`. Его ID назначаются во время работы и не равны mesh IDs из файла.

## Runtime-связи и обход

`0x1005C040` — общий рекурсивный обход с visitor:

```text
walk(node):
    if not visitor(node):
        return
    if not node.is_leaf:
        for child_id in node.children:
            if child_id != FFFFFFFF:
                walk(nodes[child_id])
```

Сам обход ничего не знает о камере, плоскостях frustum, PVS или препятствиях. Семантика задаётся visitor.

### Привязка мешей и областей окклюзии

- `0x1004CF20` собирает пересекающиеся листья по AABB, удаляет старые backlinks и добавляет объект в контейнер `node+0x6C`. При единственном старом узле, строго содержащем объект, перепривязка может не выполняться.
- `0x1004D1B0` перестраивает уникальный список областей окклюзии объекта на основании контейнеров его узлов. Это обслуживание связей, **не решение «рисовать/не рисовать»**.
- Callback `0x1005D0A0` принимает область и признак добавления/удаления. Сначала проверяется включающее касания пересечение AABB. Если **область строго покрывает узел** по всем шести границам, она попадает в `+0x4C`. Иначе, если узел — лист, используется `+0x5C`. Направление включения важно: область покрывает узел, не наоборот.
- Даже после добавления в `+0x4C` callback возвращает true, поэтому обход продолжается в пересекающиеся дочерние узлы. Нельзя предполагать хранение области только на одном верхнем уровне.
- При изменении областей связанные объекты уведомляются через `0x1004D0E0`; счётчик области `+0x30` увеличивается/уменьшается при связях. Это не счётчик сэмплов GPU.

У статического меша AABB находятся в `+0x4C/+0x58`; контейнер узлов — в `+0x64`, контейнер областей — в `+0x74`. Конструктор меша `0x1005A470` вызывает базовый `0x1004D550`, который подписывает `(this, 0x1004D500)` на событие singleton `0x10038FC0()->+0x50`. Callback сбрасывает кешированные списки и вызывает `0x1004D1B0`.

Имя события и точное место его dispatch не установлены. Вызов виртуального метода `+4` из reader меша по `0x10058E9C` **не является пространственной регистрацией**: фактический `0x10014CA0` лишь устанавливает байтовый флаг объекта `+8`.

### Источники света

`0x10056B80` связывает статические источники света с пересекающимися листьями, заполняя `node+0x7C`.

`0x1004A660` выполняет запрос освещения в точке:

1. Visitor `0x1004A420` отсекает узлы, AABB которых не содержит точку; границы включены.
2. Из подходящих листьев собираются световые указатели.
3. Повторы убираются query stamp: глобальный счётчик `0x101CEE84`, поле источника `+0x30`.
4. Проверяются расстояние и направление/конус, где применимо.
5. Затем выполняется отдельный запрос препятствия через `i_collision_system`, virtual slot `+0x38`. При обнаруженном пересечении кандидат отбрасывается. Directional lights обрабатываются отдельно от пространственного списка.

Здесь есть проверка блокировки света стенами, но это **collision-ray после broadphase**, а не сохранённая видимость листа. Глобальный `0x101CEBF8` установленно является `i_collision_system`: assertion `0x10043D38–0x10043D57`, строка по `0x101836D8`.

### Что не следует выдавать за frustum-culling

- Wrapper `0x10049630` только запускает общий обход с произвольным visitor; прямых E8/E9 и абсолютных dword-ссылок на него в исследованном PE не найдено. Это не доказывает активное применение в рендерере.
- `0x10049650` использует AABB-visitor `0x10049450`; `0x100496D0` — visitor `0x10049000`, строящий куб `query_center ± query_radius`. Оба callback только возвращают boolean, не собирая меши. Последующая выдача результата делегируется другому интерфейсу.
- `0x10049000` не является sphere–sphere, точным sphere–AABB или frustum-тестом. Он использует радиус запроса, а не сериализованный радиус узла.
- Исследованные visitors используют AABB узла, а не его центр/радиус.
- `0x10057A50–0x10057A78` отправляет render-interface меша `mesh+0x84` и идентификатор материала в менеджер из `0x1009F120`, virtual slot `+0x14`. Здесь нет обхода vistree. Последующий отбор видимой геометрии не прослежен.

## Отдельная аппаратная окклюзия и конфигурация

Создание ресурса `0x10003800` выделяет renderer query handle (`0x1000382A`, поле ресурса `+8`), сохраняет AABB в `+0x0C..+0x20` и runtime ID в `+0x34`. Результирующий флаг видимости расположен в `+0x38`.

При обновлении `0x10003928–0x10003933` в соответствующей ветке видимость выставляется при результате query **больше 10**. Есть дополнительные условия готовности/состояния и renderer-предикат `0x10046290 -> 0x100031D0`, точный смысл которого не установлен. При `r_occ_enable == 0` флаг видимости принудительно становится true (`0x10003960–0x10003970`). Конечный per-mesh потребитель этого флага в исследовании не найден.

Регистрация параметров в DLL:

- `0x1004796C–0x10047981`: `r_occ_enable` → глобальный `0x101CEE04`.
- `0x100479A4–0x100479B4`: `r_occ_use_auto_placement` → глобальный `0x101CEE0C`.

В `config_user/startup_autorun.cmd` на момент исследования записано:

```text
r_occ_enable                 1
r_occ_use_auto_placement     0
r_occlusion_cull             0
r_self_occlusion             0
r_show_occluders             0
r_show_vistree               0
```

Это содержимое конфигурационного файла, **не измеренное состояние запущенной игры**. Из него следует лишь, что данный файл не запрашивает автоматическое создание областей из листьев. Разные параметры нельзя объединять в один «окклюзия включена/выключена».

Есть отдельный путь загрузки `\%s\%s.ds2om`: `0x10056EBF–0x10056EE5 -> 0x10054B60`; строка сигнатуры `DS2OcclusionMap_1` находится по `0x1018478C`. Формат `.ds2om` не разобран в этом документе, его данные нельзя приписывать `vistree`. В дереве `gameres` файлов `*.ds2om` при поиске не обнаружено.

## Как продолжать в репозитории

В checkpoint-коде `a39ba60`:

- `inspect_ds2.py::parse_map()` читает секцию последовательно, `_node()` возвращает её записи в `metadata['vistree']`.
- Ключи записи: `offset`, `bounds_min`, `bounds_max`, `field_24`, `center`, `leaf`, `children` либо `mesh_indices`, `end`.
- `field_24` нужно интерпретировать как биты f32; в рамках этого исследования парсер не переименовывался и не менялся.
- `view_ds2.py` дерево не использует для отсечения: рендерит подготовленные списки мешей.

Для просмотра существующего JSON, из каталога игры:

```powershell
python ds2_research/inspect_ds2.py gameres/maps/map08/lastzlo.ds2 --meshes
```

Несмотря на имя флага, `--meshes` добавляет все записи в `records`, в том числе `records.vistree`. Преобразование текущего `field_24` без изменения парсера:

```python
radius = struct.unpack('<f', struct.pack('<I', node['field_24']))[0]
```

Для воспроизводимого дизассемблирования достаточно оригинальной DLL с указанным хешем, `pefile` и Capstone. Использовать `pe.get_memory_mapped_image()` и адреса RVA, а не вычитать image base из VA и применять результат напрямую к raw-файлу. Начинать дизассемблирование с известного начала функции: произвольный VA может попасть внутрь x86-инструкции.

Если следующим шагом внедрять дерево в просмотрщик, отдельной задачей потребуется: исправить имя/тип радиуса в парсере и его потребителях; реализовать frustum/AABB-обход; дедуплицировать mesh IDs; сохранить прежние правила материалов, прозрачности и instancing. Это будет собственный broadphase просмотрщика, а не заявленная копия неизвестного пути оригинального рендерера. Объекты за стенами одним таким обходом скрываться не будут.

## Не установлено

- Эвристика экспортёра: почему выбран конкретный предел глубины и где прекращается разбиение.
- Точный dispatch/name события, подписанного в базовом конструкторе меша.
- Прямой active frustum-путь оригинального рендерера через vistree.
- Конечный per-mesh draw-skip потребитель флагов аппаратной окклюзии.
- Назначение сдвига всех шести границ на `-20.0` в автоматической области.
- Формат отдельного `.ds2om`.

Сам формат записей узла, топология и соответствие leaf mesh IDs с AABB на установленном корпусе не являются предположениями. Runtime-выводы выше ограничены названными адресами; именовать неизвестные участки по аналогии с Quake/BSP/PVS нельзя.

Исследование выполнялось чтением ресурсов и статическим анализом DLL. Игра, просмотрщик и тестовые наборы в ходе разбора vistree не запускались. Исходные ресурсы и DLL не изменялись.
